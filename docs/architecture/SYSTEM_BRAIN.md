## 1. АНТИХРУПКАЯ АРХИТЕКТУРА

### 1.1. Принципы антихрупкости

**Децентрализация:** Каждый компонент живёт независимо. Падение одного не рушит систему.
- Frontend (madeirabook-site) — статика на Vercel
- Backend (madeirabook-core) — API на Vercel
- Бронь — Zeevou/Smoobu (внешние PMS)
- Платежи — Stripe Connect (прямые выплаты владельцам)

**Избыточность:** Критические пути имеют резервные варианты.
- Email: Resend + фоллбэк на Telegram
- Бронирование: Zeevou + Smoobu (два PMS)
- Уведомления: Telegram + WhatsApp + Email

**Модульность:** Одна ответственность — один модуль.
- Payload CMS — только контент
- Neon — только наша память о госте
- Внешние системы — только транзакции

**Медленные изменения:** Каждое изменение проходит через 5 фильтров.
1. Попадает ли это в одну из 6 аномалий?
2. Усиливает ли это главную аномалию — возврат гостей?
3. Работает ли это через один из инструментов?
4. Есть ли визуальный якорь?
5. Тянет ли это гостя ближе к бронированию?

**Отказ от перфекционизма:** Сделанное лучше идеального.
- MVP → тест → итерация
- 40% готово = 40%, не "почти всё"
- Проверка через 60 дней, не через 6

### 1.2. Слои данных

**Слой А — Транзакционный (внешние системы):**
- Цены, доступность, календари → Zeevou/Smoobu
- Брони, платежи, сплит → Zeevou/Smoobu + Stripe
- Мы туда только стучимся за актуальными данными.

**Слой Б — Презентационный (наша система):**
- Страницы объектов → madeirabook-platform (Next.js)
- Фото вилл/отелей → madeirabook-assets
- Описания, атмосфера → Payload CMS
- Кнопка «Book» — deep-link в Zeevou/Smoobu

**Слой В — Память о госте (Neon):**
- Профиль гостя: Telegram ID, email, имя, телефон
- Сегмент: новичок / бывалый
- Флаги: объекты с 10% скидкой
- История броней: ID заказов + ID объектов

**Критерий разделения:**
- Витрина и маркетинг → НАШЕ
- Транзакция (деньги, календарь, бронь) → ИХ

## 2. 5 РОЛЕЙ AI-ПЕРСОНАЖЕЙ

### 2.1. Architect (Архитектор)

**Ответственность:** Целостность системы, долгосрочная устойчивость.

**Принципы:**
- Одно изменение — один коммит.
- Никаких быстрых путей в обход ARCHITECTURA.md.
- Каждое решение проходит через 5 фильтров.
- Если не вижу весь файл — прошу показать, не гадаю.

**Запреты:**
- Не дублировать данные.
- Не трогать схему БД без миграции.
- Не вносить хардкоды.
- Не смешивать репозитории.

**Проверка перед действием:**
1. В правильном ли репо я работаю?
2. Не дублирую ли я в Neon то, что живёт во внешней системе?
3. Не ручной ли это костыль вместо API?
4. Не иду ли я в обход ARCHITECTURA.md?

### 2.2. Developer (Разработчик)

**Ответственность:** Реализация, качество кода, техдолг.

**Принципы:**
- TypeScript-strict mode.
- Одна функция — одна ответственность.
- Проверка типов через zod.
- Логи через pino.

**Запреты:**
- Не использовать `any`.
- Не игнорировать ошибки.
- Не оставлять TODO без срока.
- не коммитить секреты.

**Проверка перед коммитом:**
1. TypeScript компилируется без ошибок.
2. ESLint не выдаёт предупреждений.
3. Тесты проходят.
4. Никаких console.log в проде.

### 2.3. Content (Контент-менеджер)

**Ответственность:** Контент, SEO, привлечение трафика.

**Принципы:**
- Каждая страница — один визуальный якорь.
- Прямые ответы в первых абзацах.
- Schema.org на каждой странице.
- Alt-теги на всех картинках.

**Запреты:**
- Не писать "сочинения" — только факты.
- Не копировать контент.

**Проверка перед публикацией:**
1. Мета-теги (title, description).
2. Schema.org (FAQPage, Article).
3. Визуальный якорь (карта/график/круг).
4. CTA в конце страницы.
5. Внутренние ссылки (2-3 штуки).

**Ответственность:** Деплой, мониторинг, инциденты.

**Принципы:**
- Деплой только через git push.

- При поломке — Instant Rollback.
- Секреты только в .env.

**Запреты:**
- Не деплоить вручную (vercel --prod).
- Не менять прод без бэкапа.
- Не игнорировать алерты.
- Не работать без логов.

**Проверка перед деплоем:**
1. git status чист.
2. Все тесты прошли.
3. Environment variables проверены.
4. Rollback план готов.

**Ответственность:** Метрики, A/B тесты, решения на данных.

**Принципы:**

**Запреты:**

- Не игнорировать долгосрочные тренды.

**Проверка перед отчётом:**
1. Данные актуальны.

## 4. ПРАВИЛА РАБОТЫ

### 4.1. Правила GitHub

1. **GitHub — источник истины.** Если нет на GitHub — потеряется.
2. **Цепочка:** Mac → git commit → git push → GitHub → Vercel → прод.
3. **Ничего лишнего в корне.** Тесты в scripts/, временное в .gitignore.
4. **Правило зеркала:** Obsidian — источник, GitHub — зеркало для чтения.
5. **Не редактировать копию в git.** Правки только в Obsidian, потом копия обновляется.

### 4.2. Правила Neon

1. **Схема в репозитории.** Никто не меняет Neon напрямую без файла.
2. **Перед изменением — бэкап.** Neon делает автобэкапы, но проверяем.
3. **Не удалять таблицы.** Помечаем deprecated_.
4. **Одна таблица — одна ответственность.** Понятные имена.
5. **Секреты только в .env.** Не в GitHub, не в чате.

### 4.3. Правила деплоя

1. **Только через git push.** Никаких ручных vercel --prod.
2. **Vercel сам забирает.** Подписан на GitHub.
3. **При поломке:** Instant Rollback → правка в GitHub → push.
4. **Один проект — один Vercel-проект.** Имена совпадают.

### 4.4. Правила работы с файлами

1. **Длинные файлы — частями.** cat >> с маркерами (PART1, PART2).
2. **Никаких ASCII-диаграмм.** Только markdown-списки и таблицы.
3. **Проверка после каждой части.** wc -l чтобы видеть рост строк.
4. **Если не вижу весь файл — прошу показать.** Не гадаю.

### 4.5. Правила незавершённых задач

1. **НЕ удалять незакрытые задачи.** Переносить в Следующая_сессия.md.
2. **Накапливать задачи.** Новая сессия не завершена пока все старые отражены.
3. **Отложено — с датой.** Отменено — с причиной.
4. **Проверка перед закрытием:** сверить со Следующая_сессия.md.

### 5.1. Интеграции

| Stripe | Платежи | Connect, webhook |

| n8n | Автоматизация | Webhooks, сценарии |
| TheFork | Рестораны | Партнёрка, PDF |
| TravelPayouts | Перелёты | Widget, комиссии |

### 5.2. API vs Webhook

**API — мы стучимся к ним:**
- "Дай список объектов"
- "Создай бронь"
- "Проверь календарь"

**Webhook — они стучатся к нам:**
- "Оплата прошла"
- "Бронь создана"
- "Гость выехал"

Оба нужны. У нас уже работают webhook от Stripe и Telegram.

### 5.3. Smoobu API особенности

**Host:** https://login.smoobu.com  
**Authentication:** HMAC-SHA256 (Base64)

**Canonical string (6 строк через \n):**
```
<HTTP_METHOD>
<PATH>
<QUERY_STRING>
<X-TIMESTAMP>
<X-NONCE>
<SHA256_HEX_OF_BODY>
```

**Ключевые правила:**
- SHA-256 body hash обязателен ВСЕГДА.
- Пустое тело → хэш e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855
- Timestamp: ISO 8601 UTC БЕЗ миллисекунд.
- Signature output: HMAC-SHA256 → Base64 (НЕ hex).
- Secret передавать как UTF-8 string, НЕ base64-decode.
- Часы синхронизированы (5 мин drift → reject).
- Nonce: UUID v4, генерируется заново на каждый запрос.

## 6. TELEGRAM MINI APP (TMA)

### 6.1. Концепция

TMA — веб-интерфейс (React + Vite), который переиспользует Express-бэкенд.
Бот @Madeirabookbot — только точка входа. Webhook, не polling.
Аутентификация через initData.

**Схема:**
```
Telegram → @Madeirabookbot → web_app URL → TMA (React)
                                    ↓
                          Express backend (madeirabook-core)
                                    ↓
                          Neon / Stripe / Smoobu
```

### 6.2. Guest TMA

**Главная кнопка — динамическая:**

| Состояние | Кнопка |
|---|---|
| Новичок | 📅 Забронировать сейчас (−10% на следующий раз) |
| Вернулся | 🎁 Забронировать с −10% (персональная скидка) |
| Есть бронь | 🔔 Детали заезда (через X дней) |
| После заезда | ⭐ Оценить поездку 1–10 |

**Логика −10%:**
- Платформенная скидка, не per-property.
- Работает по всей сети Madeirabook.
- Владельцы подписываются через галочку.
- В канале повторов — только объекты подписавшихся.
- Скидка бессрочная (без таймера).
- Платформа отдаёт 10% из своей комиссии (12% → 2%).
- Владелец получает 88% как обычно.
- Триггер: наличие прошлой брони по telegram_id.

### 6.3. Owner TMA

**4 плитки данных:**
- 🔔 Заездов сегодня → список гостей
- 💰 Выплата → сумма, дата, разбивка
- 📅 Загрузка → % занятости, календарь
- ⭐ Рейтинг → средний балл, отзывы
- ➕ Добавить бронь → ручное добавление

### 6.4. Приоритет внедрения

TMA делаем ПОСЛЕ первых 10+ живых броней через сайт.
Сначала — ловушки (PDF, Flight Alerts, TheFork).
Потом — TMA как удержание и возврат.

## 11. SEO + GEO

### 11.1. SEO (Google)

- Прямые ответы в первых абзацах.
- Таблицы и цифры — Google любит конкретику.
- FAQ-формат — вопросы как в поиске.
- Внутренняя перелинковка — 2–3 ссылки на страницу.
- sitemap.xml — обновлять при добавлении страниц.

### 11.2. GEO (AI Search)

**Отличие:** AI цитирует конкретику, а не «сочинения».

- `llms.txt` в корне сайта.
- Schema.org `FlightOffer`, `FAQPage`, `VacationRental`.
- Прямые ответы в формате «вопрос-ответ».
- Никаких литературных текстов — только факты, цифры, структура.

### 11.3. Почему HTML > Tilda

1. **Скорость:** Edge CDN Vercel отдаёт HTML за миллисекунды.
2. **Чистота кода:** Боты читают семантический HTML.
3. **GEO:** AI легко «выдёргивает» факты из чистого HTML.
4. **Минимализм:** 4 сущности вместо 6.

## 21. ЭТАЛОН: СТРАНИЦА ОБЪЕКТА

Копировать с penthouse-view-ocean-canico.html.

**Обязательная структура:**
1. Хлебные крошки (nav aria-label="Breadcrumb")
2. Заголовок H1 = название объекта
3. Галерея фото: первое h-96, остальные сетка 2x3, все с loading="lazy"
4. Характеристики (4 плитки: m², bedrooms, beds, guests)
5. Кнопка "Book this [тип]" с UTM-метками
6. Блок About (3-4 абзаца)
7. Amenities (9 плиток с эмодзи)
8. Location (что рядом, список)
9. Блок "Other stays in Madeira" — перелинковка
10. CTA "Ready to book?" вторая кнопка
11. Футер стандартный

**Schema.org VacationRental — обязательные поля:**
- name, description, image (массив абсолютных URL)
- address (PostalAddress)
- geo (GeoCoordinates — точные координаты)
- identifier (уникальный slug)
- floorSize (QuantitativeValue с unitCode MTK)
- numberOfBedrooms, numberOfBathroomsTotal
- occupancy (QuantitativeValue, maxValue)
- containsPlace (массив Room с occupancy.value, НЕ maxValue)
- amenityFeature (массив LocationFeatureSpecification)

**Не забывать:**
- URL Zeevou deep-link: /portugal/{город}/{имя}-by-madeirabook
- UTM: ?utm_source=madeirabook&utm_medium=site&utm_campaign=property_page
- Папку для фото называть ТОЛЬКО маленькими буквами
- После создания страницы: python3 update-sitemap.py

## 22. ПРАВИЛА АССИСТЕНТА (САМОКОНТРОЛЬ)

Ассистент проверяет САМ перед каждым неочевидным решением.
Если нарушает — говорит об этом вслух.

### 22.1. Никаких ручных костылей
Если данные можно получить автоматически — берём из источника.
Пример ошибки: вручную вписать названия объектов в Neon.

### 22.2. Никаких хардкодов
Токены, ID, конфиги — только через .env и config.

### 22.3. Всё через core
TMA и site не стучатся к внешним сервисам напрямую.

### 22.4. Не дублировать данные
Если данные живут во внешней системе — не копируем в Neon.

### 22.5. В правильном репо
Перед правкой — проверить, что работаю в нужном из трёх репо.

### 22.6. Не идти в обход ARCHITECTURA.md
Если ARCHITECTURA.md говорит одно, а «так быстрее» — идём по ARCHITECTURA.md.

### 22.7. Не терять незакрытые задачи
Перед закрытием сессии — сверить со Следующая_сессия.md.

### 22.8. Если не вижу весь файл — прошу показать
Не строить догадки по куску.

### 22.9. Не ликовать рано
Пилот ≠ результат. Оценки честные.

### 22.10. Если сомневаюсь — сказать об этом
Не делать вид, что всё понятно.

### 22.11. Ассистент не видит файлы на Mac
Видит ТОЛЬКО то, что пользователь показал: скриншот, копипаст, загруженный файл.

### 22.12. Работа с выводом команд
Ассистент САМ задаёт нужную длину: head -N, tail -N, sed -n 'X,Yp', grep -n.
Не даёт "просто cat" файлов больше 40 строк.

### 22.13. Длинные файлы — частями
Если файл больше 100 строк — НЕ создавать одной командой.
Использовать cat >> с маркерами (PART1, PART2).
Проверка: после каждой части — wc -l.
